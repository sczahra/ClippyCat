# ClippyCat v2.3 manifest-driven visual actions result

## Baseline

- Starting commit: `76806803822df84c1630c5ff6c21279ee8f39292`
- Starting working tree: clean
- Starting/final atlas dimensions: 1536x3536 RGBA for Marmalade and Merry

## Previous hardcoded dependencies

Before v2.3, each ordinary visual action needed matching `PetAction` and `PetState` enum values, a hand-written tray item, enum-keyed manifest storage, enum parsing during manifest load and playback, named energy cases, a named pending fallback, and an enum round-trip for frame timing. Do Something and autonomous selection also returned visual actions as `PetAction` values.

## Architecture changes

- `VisualActionDefinition` is now the runtime model for content-driven actions.
- A case-insensitive dictionary uses the manifest's stable string `id` as the runtime key.
- The model exposes `id`, `displayName`, optional global `enabled`, optional `menuOrder`, frames, frame timing, duration bounds, tray visibility, Do Something eligibility (`randomEligible`), autonomous weight, and per-pet availability/row/source metadata.
- `PetAction` now contains only code-defined built-ins: Idle, WalkLeft, WalkRight, Wait, Rest, Wave, Jump, Groom, Paw, and Review.
- The six visual-specific `PetAction` values and six visual-specific `PetState` values were removed.
- One generic `PetState.VisualAction` and `activeVisualAction` field drive ordinary stationary sprite playback.
- Existing manifest schema version 1 remains supported. The legacy `name` property remains a runtime/importer fallback when `id` and `displayName` are absent.

No sprite art, atlas row, frame count, timing, duration, weight, or pet availability was changed.

## Generic playback

`TriggerVisualAction(string actionId)` and `PerformVisualAction` now provide the only visual-action dispatch path. They resolve the definition and current pet, set the generic visual state with the configured atlas row/frame count/duration, use the active definition's `frameMs`, and return through the existing state timer. Direct unavailable actions use the definition's display name in the existing friendly `"animation coming soon"` message.

Built-in actions retain their existing `PerformPetAction` switch because they execute code behavior. Walking, call-to-cursor, Rest, jumping, dragging, mouse look, landing, hide/show, and other mechanics were intentionally not forced into the visual manifest.

## Generic tray menu

The tray now enumerates enabled definitions with `trayVisible=true`, orders them by `menuOrder`, labels them with `displayName`, and captures their string ids for `TriggerVisualAction`. There is no named Stretch, Scratch, Yawn, Sit/Settle, Tail Flick, or Roll/Flop menu construction in `Program.cs`.

Merry Stretch remains visible because the action itself is enabled and tray-visible, but its Merry pet entry remains disabled; selecting it shows the existing friendly pending message.

## Do Something and autonomous behavior

- Do Something keeps its five existing built-in choices and adds every globally enabled, `randomEligible` visual action that has art for the active pet.
- Visual actions remain uniformly represented in the Do Something pool, preserving the previous behavior because the manifest has no separate Do Something weight.
- Autonomous selection keeps the existing low/normal/high energy probability structure and idle buckets.
- Available manifest actions consume their existing `autonomousWeight` inside those buckets.
- Missing or disabled pet artwork is filtered before selection, so autonomous behavior cannot show a pending popup.
- Existing totals remain 10 for Marmalade and 7 for Merry, within the 12-point smallest idle bucket.

## Manifest validation

The importer now validates:

- duplicate stable ids, case-insensitively
- required display names for new-style entries
- lowercase kebab-case explicit ids
- positive frame counts within atlas column capacity
- positive frame timing and valid duration bounds
- autonomous weights from 0 through 12 and per-pet totals no greater than 12
- non-negative optional menu order
- required `pets` metadata
- unknown pet names
- required Marmalade and Merry entries
- non-empty source folders
- protected/duplicate rows and required rows for enabled pet entries

Runtime applies the same essential structural, timing, row, pet-name, and weight checks. A malformed optional entry is skipped and included in one consolidated warning while valid definitions remain loaded. A malformed global document still degrades safely to no visual definitions rather than crashing the pet.

Global `enabled` defaults to true when omitted. `menuOrder` defaults to manifest order after explicitly ordered entries. Disabled actions do not appear in the tray or selection pools and are not imported.

This proves a future ordinary visual action can be discovered without a new enum value, manual menu item, or action-specific dispatcher branch.

## Build-and-run workflow

`Build-And-Run-Actions.ps1` already remains the single normal command: it invokes the importer, builds the project, verifies the executable, and launches ClippyCat. No script change was necessary.

Exact future workflow:

1. Create `Assets/actions/<Pet>/<action-id>/` for supported pets.
2. Add sequential transparent RGBA frames named `0.png`, `1.png`, and so on, no larger than 192x208.
3. Add one `actions.json` entry with a lowercase kebab-case id, display name, unused row, frame/timing/duration data, eligibility, weight, ordering, and both pet configurations.
4. Run `./Build-And-Run-Actions.ps1`.
5. Test the tray command, Do Something, autonomous frequency, and missing-pet behavior.

No `Program.cs` edit or enum addition is required for an ordinary stationary visual action. Custom movement, physics, sound, desktop interaction, or scripted paths may still require code.
