# ClippyCat v2.3 manifest-driven visual actions plan

## Baseline

- Starting commit: `76806803822df84c1630c5ff6c21279ee8f39292`
- Starting working tree: clean
- Existing manifest schema version: 1
- Existing visual rows: Stretch 11, Scratch 12, Yawn 13, Sit/Settle 14, Tail Flick 15, Roll/Flop 16
- Existing atlases: 1536x3536 RGBA

## Remaining hardcoded per-action dependencies

`Program.cs` currently requires every manifest visual action to have:

- a named `PetAction` enum value
- a named `PetState` enum value
- a manually constructed tray item and menu insertion
- an `Enum.TryParse` mapping from manifest `name` to `PetAction` during load
- an `Enum.TryParse` mapping from manifest `name` to `PetState` during playback
- enum-keyed availability, Do Something, and autonomous-selection helpers
- a named `PetState` case in energy accounting
- a named `PetAction` pending fallback case
- an enum round-trip in `GetFrameDelay` to recover manifest timing

The importer also treats `name` as both machine identity and user-facing text, and it does not reject unknown extra pet names. Runtime manifest failure currently discards every visual action even when only one optional entry is bad.

## Proposed runtime action model

Use a small `VisualActionDefinition` model keyed by a stable string `id`. It will expose:

- `id` and `displayName`
- existing frame count, frame timing, duration, tray visibility, Do Something eligibility (`randomEligible`), autonomous weight, and per-pet row/source availability
- optional global `enabled` flag, defaulting to true
- optional `menuOrder`, defaulting to manifest order

The runtime will store definitions in a case-insensitive `Dictionary<string, VisualActionDefinition>`. A single `PetState.VisualAction` will represent ordinary stationary sprite playback, while a field tracks the active definition so frame timing remains manifest-driven.

One `TriggerVisualAction(string actionId)` / generic playback path will resolve the current pet, enter row/frame/duration metadata, and show the existing friendly pending message only for direct unavailable commands. It will never use action-specific string comparisons or row constants.

## Built-in and mechanical coexistence

`PetAction` remains for behavior that genuinely executes code: idle, walking, waiting/resting, wave, jump, grooming, paw/review reactions, and their existing movement/state transitions. Dragging, mouse look, call-to-cursor, hiding/showing, and landing remain code-defined.

Manifest visual actions will be selected separately by string id. Do Something will keep its five existing built-in reactions and append available manifest visual actions. Autonomous selection will continue using the existing idle buckets; visual entries consume their configured weights inside those same buckets, preserving the surrounding behavior probabilities.

## Migration plan

1. Add `id`, `displayName`, `enabled`, and `menuOrder` support while retaining the existing timing, eligibility, and per-pet structure.
2. Migrate the six current manifest entries to lowercase kebab-case ids without changing rows, frames, timing, weights, or availability.
3. Replace the six named visual `PetAction` and `PetState` values with one generic `PetState.VisualAction` and active-definition tracking.
4. Replace the six manual tray items with manifest-ordered dynamic items.
5. Route direct tray, Do Something, and autonomous visual choices through the generic string-id path.
6. Strengthen runtime and importer validation for duplicate ids, display names, rows, frame/timing/duration/weight metadata, supported pet names, and complete per-pet configuration.
7. Prove content-only discovery with a temporary disabled `manifest-proof` entry, build/import validation, and runtime-loader inspection; remove it before the final commit.
8. Run the importer twice, build, verify unchanged atlas hashes/rows, checkpoint, commit, and push.

## Backwards compatibility

- Schema version 1 remains supported.
- Runtime and importer accept the legacy `name` property as both id and display-name fallback only when the new properties are absent.
- Existing production entries will be migrated to explicit `id` and `displayName` fields.
- Missing `enabled` continues to mean enabled; missing `menuOrder` falls back to manifest order.
- A malformed optional entry is skipped with one consolidated warning while valid entries remain available. A malformed global manifest still leaves visual actions safely pending instead of crashing the pet.
- Existing art, rows, timing, availability, and behavior weights remain unchanged.

## Explicitly out of scope

- New artwork or a new production action
- Merry Stretch artwork
- Converting mechanical/movement actions to the visual manifest
- Settings, diagnostics, sprite pipeline, rendering, or behavior-engine redesign
- Packages, plugin systems, sound, desktop-icon interaction, scripted paths, or installer work
- Changes to existing atlas pixels or visual-action timing/weights
